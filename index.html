AI Worklog / Как я работал(а) с AI

Шесть чекпоинтов работы: от постановки задачи до финальной проверки. Без переписки целиком и без приватных данных.

Как я сформулировала первую задачу для AI

Сначала PRD, потом код

Я не просила «сделай приложение про лис». Сначала я написала PRD (PRD_Лисий_диспетчер.md) и только потом отдала его AI как единый источник требований — так у модели не оставалось места для додумывания.

  • Роль и пользователь: лесной смотритель, которому нужен рабочий инструмент, а не аналитический дашборд.
  • Формат: один HTML-файл с vanilla JS, без сборки и внешних зависимостей — чтобы тестовое открывалось двойным кликом.
  • Что должно считаться: уникальные лисы, активные локации, рейтинг подозрительности, самая подозрительная лиса, объяснение вывода и текстовый отчет.
  • Явное ограничение: данные живут в JS-состоянии и меняются через интерфейс, никакого бэкенда.

Как я просила AI помочь со структурой и интерфейсом

Сначала раскладка экрана, потом логика

Я отдельно попросила AI предложить разбивку экрана и порядок блоков — до написания кода. Обсуждали не «как назвать функции», а что смотритель видит первым.

  • AI предложил разделить экран на пять зон: панель управления (фильтры и веса), метрики, таблица наблюдений, карта активности, рейтинг + отчет.
  • Я попросила отдельно вынести объяснение расчета, чтобы score не выглядел «магическим числом».
  • По архитектуре кода договорились на простую схему: одно состояние state → чистые функции расчета (filterObservations, calculateFoxRanking, buildReport) → один render(). Никаких классов и фреймворков.
  • Просила именно так, потому что мне как PM важно уметь прочитать логику расчета, не разбираясь в реактивности.

Какие решения приняла сама, а что изменила после ответа AI

Формула score — мое решение

  • Решила сама: формула остается линейной и читаемой — средняя подозрительность × вес + добыча × бонус + повторные появления × бонус. AI предлагал более «умный» вариант с нормализацией и затуханием по времени — отклонила: смотритель не должен догадываться, откуда взялось число.
  • Решила сама: веса вынести в интерфейс ползунками, а не зашивать в код — иначе нельзя показать, что выводы меняются вместе с параметрами.
  • Изменила после AI: согласилась на детерминированную сортировку рейтинга с тай-брейкерами (score → средняя подозрительность → id), иначе при равных score порядок «прыгал».
  • Изменила после AI: добавила repeatCount = observationCount − 1 вместо простого счетчика наблюдений — лиса с одним появлением больше не получает бонус за «повторность».
  • Отклонила: localStorage и график по времени — вне объема задания, добавляли риск без пользы для проверки.

Как дорабатывала логику, UX/UI и поведение интерфейса

Несколько итераций поверх первой версии

  • Живой пересчет: любой фильтр, ползунок или правка ячейки пересчитывают метрики, карту, рейтинг и отчет сразу, без кнопки «применить».
  • Inline-редактирование: в первой версии наблюдения были только для чтения. Добавила правку прямо в таблице — по PRD пользователь должен менять данные, а не только смотреть.
  • Объяснимость: у каждой лисы в рейтинге появилось текстовое объяснение (buildFoxExplanation) — какой вклад дала подозрительность, добыча и повторы.
  • Подсветка лидера: самая подозрительная лиса выделяется одновременно в таблице и в рейтинге, чтобы связь между блоками читалась без поиска глазами.
  • Карта: активная локация подсвечивается по текущей выборке, а не по всем данным — иначе карта противоречила фильтрам.
  • Статусы: разделила сообщения формы, загрузки JSON и таблицы. Раньше был один общий блок, и ошибка JSON перетирала подтверждение добавления записи.
  • Пустое состояние: при нулевой выборке вместо пустой таблицы — понятный текст и рекомендация расширить фильтры.

Какие ошибки и слабые места нашла и как исправила

Что сломалось при проверке

  • Дубли id при загрузке JSON. Валидация проверяла поля по одной записи и пропускала повторяющиеся id — рейтинг молча склеивал наблюдения. Добавила validateObservationList с проверкой уникальности по всему массиву.
  • Мусор в данных. suspicion_level приходил строкой или вне диапазона. Добавила sanitizeObservation: приведение типов, обрезка в 0–10, Boolean для has_prey, регулярка на формат времени HH:MM.
  • Деление на ноль и пустая выборка. При фильтре без результатов ломался расчет средней и отчет. Теперь пустой случай обрабатывается отдельной веткой с текстом для смотрителя.
  • XSS через поля. Локации и цвета вставлялись в разметку как есть. Добавила escapeHtml на все пользовательские значения — включая те, что попадают в отчет.
  • Русская морфология. В отчете было «3 наблюдение». Написала pluralRu — мелочь, но именно она выдает сырой прототип.
  • Нестабильная сортировка при одинаковых score — закрыта тай-брейкерами (см. шаг 3).

Как проверяла финальный результат

Прогон по сценариям, а не «вроде работает»

Проверяла руками в браузере по списку сценариев, каждый раз сверяя четыре блока сразу: метрики, карту, рейтинг и текст отчета.

  • Стартовые данные из задания — цифры сошлись с ручным пересчетом формулы.
  • Фильтры до пустой выборки — корректное пустое состояние без ошибок в консоли.
  • Битый JSON, JSON не-массивом, запись без поля, suspicion_level = 15, время «25:00» — каждый случай дает конкретное сообщение с номером записи, а не общее «ошибка».
  • JSON с дублирующимися id — загрузка отклоняется.
  • Крайние значения весов (0 и максимум) — лидер рейтинга меняется предсказуемо, объяснение соответствует новым числам.
  • Добавление, редактирование и удаление наблюдения — состояние и все производные блоки пересчитываются согласованно.
  • Сброс фильтров и сброс данных возвращают приложение в исходное состояние.
  • Отдельно проверила соответствие финального файла пунктам PRD — построчно по разделу требований.
